2. Plain-English summary

This file powers the primary authenticated home view in TeamForge. It fetches live data from users, projects, tasks, join requests, and mentorship badges to compute live statistics such as XP and reputation points. It displays a dynamic 5-item recent activity timeline merging notifications and user project actions. Users can also add and remove skill chips through a controlled input, which automatically persists updates to the NestJS backend. All external API calls are safely isolated with fallback mechanisms so that a failure in one service never crashes the entire dashboard.

6. Data flow

Data originates from AuthContext (user), NotificationContext (notifications), and localStorage (teamforge.backendUserId, teamforge.role). In fetchDashboard, HTTP GET requests are dispatched to /users/:id (UsersController.findById), /projects (ProjectsController.findAll), /join-requests (JoinRequestsController.findAll), /mentorship/badges/:userId, and /tasks. Headers include x-user-role and x-user-id. The raw responses are filtered and transformed into stats and userActions states. Skills management is handled centrally via Settings (/settings), which dispatches PATCH requests to /users/:id via usersApi.update with payload { profile: { skills } }.

Q4: How are XP and reputation derived in this view? Lines 240–257

Model Answer: Lines 240–257 filter user tasks that are 'completed', 'approved', or 'done'. XP sums each task's reward via getTaskReward(t.priority).xp, while reputation is calculated as approvedTasks.length * 8.

Model Answer: Lines 326–329 attach window listeners for 'teamforge:task_updated', 'teamforge:project_updated', and 'teamforge:notification_updated'. When any component dispatches these events, fetchDashboard immediately re-executes.

Fallback ID '1' on line 73 is a convenience fallback for mock testing, but in production, routes must strictly require authenticated IDs. function App() {

  const [maintenanceMsg, setMaintenanceMsg] = useState('');
  const isAdminRoute = typeof window !== 'undefined' && window.location.pathname.startsWith('/admin');
  useEffect(() => {
    const handleMaintenanceEvent = (e) => {
      if (!window.location.pathname.startsWith('/admin')) {
        setMaintenance(true);
        if (e.detail?.message) setMaintenanceMsg(e.detail.message);
      }
    };
    window.addEventListener('teamforge:maintenance', handleMaintenanceEvent);
    if (!isAdminRoute) {
      adminApi.getPublicConfig().then(cfg => { if (cfg?.maintenanceMode) setMaintenance(true); });

  }, [isAdminRoute]);

22. Back-end Module: auth

1. Where it is and its size

  • Full Path: back-end/src/auth (auth.controller.ts: 52 lines, auth.service.ts: 282 lines, DTOs: 33 lines)
  • Role in App: Password reset lifecycle management, SHA-256 token hashing, strict in-memory rate limiting, and audit logging.

2. Plain-English summary

The auth module implements secure password recovery in TeamForge without exposing account enumeration vulnerabilities. It exposes POST /auth/forgot-password and POST /auth/reset-password. When a user requests a reset, it applies an in-memory sliding window rate limiter (max 5 attempts per identifier per hour) and generates an unguessable 32-byte cryptographic token. The token is hashed with SHA-256 before storage in an in-memory repository with a 15-minute expiry. When resetting, the hash is matched, verified against expiration and previous use, and the user's password is updated via UsersService.

Module Endpoints & Architecture

POST /auth/forgot-password

Summary: Request a password reset link for an email or username.

Guards / Security: Public (no role guard; protected by in-memory rate limiting)

DTO Validation: ForgotPasswordDto (@IsString(), @IsNotEmpty() identifier)

Service Execution (Step-by-Step): 1. Sanitizes identifier. 2. Checks rate limiter: rejects with 429 Too Many Requests if >5 requests in 1 hour. 3. Looks up user via UsersService.findByEmail or findByUsername. 4. If user not found, logs info and returns 200 generic message (prevents account enumeration). 5. If found, generates 32-byte raw token via crypto.randomBytes(32).toString('hex'). 6. Hashes token with SHA-256. 7. Stores { id, userId, tokenHash, expiresAt: now + 15m, used: false } in resetTokens array. 8. Dispatches audit log and user notification. 9. Returns 200 { message: 'If an account exists, a reset link has been generated', resetLink }.

Storage: AuthService.resetTokens: PasswordResetTokenRecord[] (in-memory)

Returns: { message: string, resetLink?: string }

Possible Error Responses: 429 Too Many Requests (rate limit exceeded), 400 Bad Request (validation failure)

POST /auth/reset-password

Summary: Reset password using token received via reset link.

Guards / Security: Public

DTO Validation: ResetPasswordDto (@IsString(), @IsNotEmpty() token; @IsString(), @IsNotEmpty(), @MinLength(6) newPassword)

Service Execution (Step-by-Step): 1. Computes SHA-256 hash of incoming token. 2. Searches resetTokens array for matching tokenHash. 3. If missing, used === true, or expiresAt < now, throws 400 BadRequestException ('Invalid or expired reset token'). 4. Fetches user via UsersService.findById(record.userId). 5. Updates user password via usersService.update(userId, { password: newPassword }). 6. Marks record.used = true. 7. Informs auditService and notificationsService. 8. Returns 200 { message: 'Password reset successful' }.

Storage: Updates target token record in resetTokens; updates user in UsersRepository

Returns: { message: 'Password reset successful' }

Possible Error Responses: 400 Bad Request ('Invalid, used, or expired token' or password < 6 chars)

Top 10 Things You Must Remember for the Viva

Core conceptual anchors, architecture trade-offs, and golden examiner answers.

Tip #1

Explain State Lifting Confidently (Layout vs Navbar)

When asked how the hamburger button in Navbar collapses the Sidebar, explain that the isSidebarOpen state is lifted up to layout.jsx. Layout passes a callback function toggleSidebar down to Navbar as onMenuClick, and passes the boolean isOpen down to Sidebar. When the user clicks the menu button, the callback triggers in Layout, updating state and cascading the new prop down to Sidebar.

Tip #2

Master the Controlled Components Pattern

Whenever asked about FormInput.jsx, Login.jsx, or Signup.jsx, state clearly: 'A controlled component is an input whose value is bound directly to React state (value={state}) and whose mutations are delegated to an event handler (onChange={(e) => setState(e.target.value)}). React is the single source of truth for the input's state at all times.'

Tip #3

Know Exactly Why useCallback is Used in dashboard.jsx and NotificationContext.jsx

Examiners love asking about useEffect dependency arrays. Explain that functions in JavaScript are compared by reference. If fetchDashboard or fetchNotifications were declared as regular functions, they would get a new memory reference on every render cycle. Because they are listed in useEffect dependency arrays, this would cause an infinite re-render loop. useCallback memoizes the function reference so it only changes when its dependencies (like user?.id) change.

Tip #4

Explain Optimistic UI Updates in NotificationContext.jsx

When markAsRead is called in NotificationContext, it immediately updates local React state before the asynchronous HTTP request finishes. Explain that this eliminates UI latency for the user—the unread count badge in Navbar drops to zero and the notification dims instantly. If the backend request fails, the error is logged without jarring the user interface.

Tip #5

Be Honest About In-Memory Repositories and Authentication Headers

Never claim this project has an enterprise PostgreSQL database or JWT tokens if it does not. Confidently explain: 'For our university project and live demonstration, we implemented an in-memory repository architecture with pre-seeded test data, and passed user identity via x-user-id and x-user-role headers. In an enterprise production deployment, we would replace these with an ORM like TypeORM or Prisma connected to PostgreSQL, and use cryptographically signed JWT cookies with refresh token rotation.'

Tip #6

Understand the Provider Nesting Order in App.jsx

Explain the hierarchy clearly: ErrorBoundary wraps the entire tree to prevent white-screen crashes. AuthProvider must wrap RoleProvider and NotificationProvider because both require user identity from AuthContext. UIProvider sits below to supply design tokens to all routed components. NotificationProvider wraps AppRoutes so every page can display alerts.

Tip #7

Explain the Ref + Mousedown Click-Outside Pattern in navbar.jsx

To explain how dropdowns close when clicking elsewhere on the page, state that useRef() holds references to the DOM nodes of the dropdown containers (roleDropdownRef and profileDropdownRef). In useEffect, a document 'mousedown' listener checks whether the clicked element (!ref.current.contains(event.target)) is outside the menu, closing the dropdown if true.

Tip #8

Know Why onBlur Was Chosen for Username Availability in Signup.jsx

Explain that performing availability checks on onChange would fire a network request on every single keystroke, causing high server load and race conditions. Using onBlur verifies availability as soon as the user finishes typing and leaves the field, providing immediate feedback before the submit button is clicked.

Tip #9

Explain Custom Window Events for Decoupled Synchronization

Point out how notificationsApi.js dispatches window.dispatchEvent(new CustomEvent('teamforge:notification_updated')). This decouples the API service from individual components, allowing independent subtrees (Dashboard, Navbar, Notification Center) to listen for the event and automatically refresh their data without prop drilling.

Tip #10

Explain the Account Enumeration Protection in the Auth Module

In the backend auth module, POST /auth/forgot-password returns HTTP 200 with a generic message ('If an account exists, a reset link has been generated') regardless of whether the user exists. Explain that returning 404 would allow malicious actors to enumerate valid student usernames and emails.
